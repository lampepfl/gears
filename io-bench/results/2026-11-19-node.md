- gears: `3f300699`
- machine: Apple M3 Max, macOS 27.2.1
- Node.js: v26.5.0

them (Scala.js on WebAssembly, with JSPI), beside the same scenarios written in plain Node.js
(`io-bench/stacks/node/bench.mjs`). Microseconds per op, lower is better. Each is the median of 8 runs at scale 1.0:
4 processes of each, taken in turn, each running the scenarios twice. The range is of those 8.

| tcp-stream | 20.82 | 14.54 | 1.43 | 20.15 to 21.98 | 13.60 to 16.05 |

| udp-connected | 27.85 | 25.58 | 1.09 | 27.56 to 28.09 | 25.13 to 25.95 |

The backend as it was merged (`9746c972`), with its own op and handle machinery, measured the same way earlier the
same day, 6 runs: 26.43, 15.48, 23.50, 92.45, 39.98, 28.84, 28.32. The machine ran a few percent slower at some
times of the day than at others, for both programs: a figure here is to be set beside the one next to it, taken in
the same minutes, and no other.

## What the difference is

The two make the same calls to Node, handle the same number of events and take the same number of turns of the
event loop (counted for `tcp-concurrent`: 640000 writes, 640000 events, about 10100 turns each). What differs is the
process's own time, not the system's. A future that waits on an op is suspended and resumed, where the plain program
is called back: for each side of a round trip, the op's own state, a promise, a microtask and the switch back to the
future's stack, each a few tenths of a microsecond. Timed inside the backend, on `tcp-concurrent`, before the last
four changes below:

| | ns |
|---|---:|
| setting up a wait: the read's first try, its place as the handle's waiter, a promise | 410 |
| from the promise resolved to the performer running again | 310 |
| leaving the wait and the op | 170 to 200 |
| the write op around Node's `socket.write` | 400 to 700 |
| the handle's report, with the read and its copy | 300 |

Adding that much work before each write in the plain Node.js program costs it the same: 2.2 us of it before each
write takes it from 8.6 to 14.0 us.

Beside that, by scenario:

- `tcp-stream` copies each 64 KiB chunk twice, into a chunk Node keeps and out of the one Node hands over, where the
  plain program writes one buffer again and again and reads without copying. Reading into a pool's buffers
  (`IntoPool`) takes Node's chunk as it is; there is no such write.
- `tcp-connect`: the backend's server closes the connection it accepted, where the plain program ends its output and
  leaves Node to close it once the client has; in the plain program that alone costs about 3 us. The rest is the
  five or so waits a connection takes.
- The UDP scenarios: the backend's send waits for Node to say the packet was sent, which is what holds a sender back
  when Node's queue of packets grows, and what gives the op its failure. The plain program sends and goes on, its
  failures an event of the socket's, which in a strict round trip is correct and never has more than one packet
  waiting. Go's and Tokio's sends, in the table of stacks, wait as the backend's do.

## What changed the figures

In the order made, each measured back to back with what was there before:

- **The performer waits on a promise where it stands** (`Parking`). gears' own `Async.await` in a future resumes by
  starting a stack, for every wait: `udp-connected` 40.3, `udp-pingpong` 55.1, `tcp-concurrent` 20.0 with it.
- **No turn of the event loop forced on every 32nd op that did not wait**: `timer-zero` 0.47 us an op, then 0.16. A
  performer now waits a turn at every 256th such op. Counting them within one turn of the loop, by asking the loop
  to announce each, was tried between the two and cost `tcp-pingpong` a call to Node for every round trip, 1.0 of
  its 16.3 thousand million instructions.
- **No callback for a write**: Node says what it still holds (`writableLength`). **A datagram socket keeps the last
  address each way**, where each packet's sender was read out of text with a regular expression: `udp-pingpong`
  41.7 to 34.6. **An op performs as its kind does**, not matched class by class.
- **A read, a write and a datagram's send are each one call to JavaScript**, in a module imported as the program
  loads: 3% fewer instructions on `tcp-concurrent`, about 0.2 us for each side of a round trip.
- **A stream is read as Node's flowing streams are**, a waiting read taking each chunk as Node hands it over:
  `tcp-concurrent` 13.7 against 14.8, 4% fewer instructions.
- **A connection's addresses are asked of Node when they are asked for**: `tcp-connect` 87 against 97.

## What was tried and not kept

- **Waking the performer from JavaScript, to do the read on its own stack**: Node's `data` event resolved the waiting
  promise with no call into WebAssembly. 2% more instructions and 2 to 3% slower on `tcp-concurrent`: what the
  performer then did for itself cost more than the two calls saved.
- **One slot in a future's group for its wait**, in place of adding the wait to the group's set and removing it:
  about 1250 instructions a wait, 0.11 us, and about 850 when done in gears' own `await` for every future on
  Scala.js, which also does away with `Parking`. Kept as the branch `experiment/js-await-in-place`, not tested.
  Reusing one listener for a group's waits saved nothing more.
- In plain Node.js, to see what the backend's way of using Node costs by itself: reading in paused mode (0.4 us a
  side), a new `Uint8Array` or a pooled `Buffer` for each write, a callback for each write, the handler run from a
  microtask. None moved `tcp-concurrent` by more than 0.5 us.
- A suspension by JSPI alone, in a module of a few instructions: 55 ns, or 80 ns over 128 stacks, against 24 ns for
  an `await` in JavaScript.

## Measuring it

V8's profiler, and `sample`, attribute time spent on a suspended stack poorly: the first charges it to the last
call into Node made there (`writeBuffer`), which looked like slow writes and was not. `socket.write` timed directly
takes 2.2 us from the backend and 1.9 us from the plain program. What could be trusted: `/usr/bin/time -l` for the
process's own time against the system's and for instructions retired, which repeat to a part in a few hundred where
times do not; a module loaded before the program (`--import`) that wraps and times Node's own calls and prints the
event loop's counts (`performance.nodeTiming.uvMetricsInfo`); and counters inside the backend.

## The realistic scenario

`tcp-realistic` (`io-bench/stacks/README.md`): a session cache that speaks Redis's protocol and its clients, over 64
connections, at `1c3f131f`. The median of 8 runs, 4 processes of each taken in turn, each running the scenarios twice.

| scenario | gears on Node.js | plain Node.js | ratio | range, gears | range, plain |
|---|---:|---:|---:|---:|---:|
| tcp-realistic | 18.26 | 11.22 | 1.63 | 17.21 to 21.14 | 10.82 to 11.64 |
| work-realistic | 1.25 | 0.68 | 1.84 | 1.17 to 1.30 | 0.66 to 0.71 |
| tcp-concurrent, in the same runs | 13.22 | 8.99 | 1.47 | 12.92 to 14.05 | 8.78 to 9.34 |

The work a program does around its I/O does not make the difference small: it adds to it. A request and its answer
take 7.0 us longer than in plain Node.js, where an echo of 64 bytes takes 4.2 us longer. Of the 2.8 us more, 0.6 us
is the work itself, which WebAssembly does in 1.25 us where V8 does it in 0.68; the rest was not measured apart, and
is most likely the bytes, a few hundred each way, moved between the program's arrays, which are WebAssembly's, and
the buffers the backend reads and writes, which are JavaScript's. The process's own time is 1.6 s against 0.8 s, and
the system's the same, 0.9 s.

The buffers matter more than that: the bench's are direct. With buffers on the heap (`ByteBuffer.allocate`), whose
bytes JavaScript cannot reach, the backend copied through an array converted a byte at a call: `tcp-concurrent` took
17.0 us where it takes 13.0, and `tcp-stream` 683 us a chunk of 64 KiB where it takes 22, some 10 ns a byte. The
backend now moves such bytes 32 at a call, packed into eight words (`NodeGlue.pour` and `spill`):

| buffers | tcp-realistic | tcp-concurrent | tcp-stream |
|---|---:|---:|---:|
| on the heap, before | 20.9 | 17.2 | 683 |
| on the heap, now | 17.7 | 13.9 | 218 |
| direct | 18.3 to 20.0 | 13.0 | 22 |

A chunk of 64 KiB is still ten times what it costs from a direct buffer, 1.5 ns a byte. `tcp-realistic` is no slower
on the heap than direct, and in these runs a little faster: its program fills and reads its buffers from arrays,
which between an array and a buffer on the heap is a copy within WebAssembly. By way of text, each byte a character,
which Node writes and reads as a block, was tried first and took twice as long as before, 1288 us: a string is made
of an array of characters, and an array of a string, a character at a call.

## Requests sent together

`tcp-realistic-bulk`: the realistic scenario with its requests pipelined, 16 at once, at the commit after `774d8f21`
that adds it. The median of 8 runs, 4 processes of each taken in turn, each running the scenarios twice.

| scenario | gears, direct buffers | gears, buffers on the heap | plain Node.js | ratio, direct | ratio, heap |
|---|---:|---:|---:|---:|---:|
| tcp-realistic | 18.52 | 17.88 | 11.98 | 1.55 | 1.49 |
| tcp-realistic-bulk | 4.90 | 3.42 | 1.73 | 2.83 | 1.98 |
| work-realistic | 1.24 | 1.23 | 0.71 | 1.75 | 1.73 |

Both programs make the same calls to Node: 16001 writes and as many reads for 128000 requests, a wait for every
eight requests on each side. With the waits gone, a request costs the backend 3.2 us more than plain Node.js where
it cost 6.5 us more one at a time, but it is now 2.8 times as long, not 1.5: what is left is not I/O. Of the 3.2 us,
0.5 us is the work, and most of the rest is the request's and the answer's bytes, some 2.2 KiB a request counting
both sides, moved between the program's arrays and the buffers it reads and writes, which with direct buffers is a
byte at a time in Scala.js's own library, on either side of the backend. With buffers on the heap that copy is
within WebAssembly and the backend's is 32 bytes at a call: 1.7 us more than plain Node.js.

## Answers gathered

`tcp-realistic-gather`: the pipelined scenario with the server's answers written as their parts, a value's own buffer
among them, by a gathering write. The median of 8 runs, as above, in runs of their own.

| scenario | gears, direct buffers | gears, buffers on the heap | plain Node.js |
|---|---:|---:|---:|
| tcp-realistic-bulk | 5.05 | 3.54 | 1.77 |
| tcp-realistic-gather | 6.20 | 3.42 | 1.74 |

Gathering changes nothing for plain Node.js, and little for the backend with buffers on the heap. With direct buffers
it costs 1.15 us a request more than copying every answer into one buffer: where that goes was not measured. The
server does more with buffers themselves here, views of them, one put into another, lines put into one, and each is
Scala.js's library working on memory that is JavaScript's; and the backend copies each of an answer's parts into the
chunk it gives Node with a call apiece, some 40 for a batch. No scattering read was tried: the protocol is read
where its bytes are contiguous, and a read into several buffers would have them copied together again.

## fs2-io on Scala.js

The realistic scenarios and the echo on fs2-io 3.16.0 and Cats Effect 3.7.1 for Scala.js 1.22.0
(`io-bench/stacks/fs2-js`), built to JavaScript and to WebAssembly, beside the gears backend and plain Node.js, all on
Node.js v26.5.0. The median of 3 runs of each, one process a run, taken in turn. The gears backend's column is with
buffers on the heap, as the bench was last linked.

| scenario | plain Node.js | gears on Node.js | fs2-io, JavaScript | fs2-io, WebAssembly |
|---|---:|---:|---:|---:|
| tcp-concurrent | 8.81 | 13.96 | 196.15 | 255.55 |
| tcp-realistic | 11.28 | 17.87 | 208.42 | 258.42 |
| tcp-realistic-bulk | 1.64 | 3.25 | 16.16 | 18.79 |
| tcp-realistic-gather | 1.65 | 3.33 | 16.55 | 19.12 |
| work-realistic | 0.67 | 1.19 | 2.02 | 1.11 |

A read and a write on fs2-io for Scala.js cost some 100 us of the process's own time each, whichever way it is
built: the echo retires 3.4 million instructions a round trip, with no more turns of Node's event loop than the
others take (19000 for 32000 round trips over 64 connections) and no timers. It is the library's own work for a read,
not anything this program adds: `tcp-concurrent` is the echo of the JVM stack (`../fs2`), a `readN` and a `write`.
Sent 16 together, a request costs a sixteenth of two reads and two writes, and the rest is what the other scenarios
show.

The work alone is the other way about: WebAssembly does it in 1.11 us where the same Scala built to JavaScript takes
2.02, as the same program measured apart did (1.04 against 1.90). With I/O, the WebAssembly build is the slower by a
quarter: what fs2-io and Cats Effect do for a read is quicker as JavaScript.
